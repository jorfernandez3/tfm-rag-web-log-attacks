\chapter{Dataset and Implementation}\label{dataset-and-implementation}

This chapter describes the experimental dataset and implementation. It
covers the dataset's public basis and schema, clean and adversarial
examples, Prompt Injection placement, the technology stack, and relevant
implementation and security considerations.

Chapter 3 defines the experimental dataset dimensions and paired design
in Section~\ref{dataset-methodology}. Chapter 4 describes how a record is
represented and processed by the assistant in Sections
\ref{input-representation} and \ref{preprocessing-and-parsing}. This
chapter connects those decisions to the dataset's composition, intended
use, and current implementation status.

\section{Dataset Overview}\label{dataset-overview}

The primary experimental dataset contains 500 synthetic web-application
log records based on HTTP CSIC 2010 request structures and attack
patterns: 250 clean records and 250 adversarial records, organized into
250 clean/adversarial pairs. The records can be examined by condition
and traffic category; these views represent the same 500 examples and
are not additional independent samples.

The 500 records were constructed synthetically for this thesis using
HTTP CSIC 2010~\cite{csic2010dataset} as the basis for representative
request structures and web-attack patterns. They are not the original
CSIC transactions or a direct row-by-row relabelling of them; no CSIC
source-row identifiers are retained. The labels, pair identifiers,
Prompt Injection text, and balanced composition were created for this
controlled evaluation.

The 500-record synthetic corpus is used as a controlled benchmark, not
as a statistically representative sample of production web traffic.
Its 250 clean/adversarial pairs enable comparison of specified injection
scenarios against their corresponding clean records, while explicit
labels support consistent evaluation across C1--C4, including correct
classifications, abstentions, and errors. The corpus therefore supports
a diagnostic comparison under defined conditions; it does not estimate
real-world attack prevalence, generalization, or deployment accuracy.
Its attack patterns and labels reflect design choices and may not
capture the diversity of operational traffic. Results are consequently
interpreted as descriptive evidence for these scenarios. Five records
informed prompt development, and the ModSec-WP pilot informed secure
prompt v5; neither evaluation is an untouched holdout.

The external evaluation dataset is a study-defined ModSec-WP sample
containing 800 records arranged in 400 pairs. Each pair combines one
sampled source request and one study-authored adversarial copy,
preserving the original web-event label. The reported quantitative
analysis uses 600 records in 300 pairs after excluding the
\texttt{bruteforce} stratum and its 100 paired copies. That category
requires evidence across a time window and is retained only for a
separate source-context audit. ModSec-WP is analyzed separately from the
500-record CSIC-based synthetic experimental dataset.

HTTP CSIC 2010 is the design basis for the primary synthetic
experimental dataset, not the external evaluation dataset. External
evaluation instead uses the ModSec-WP sample and its paired Prompt
Injection augmentation, described below.

The dataset is restricted to web application logs. Firewall, EDR, DNS,
IDS, Suricata, and Windows event logs are outside the experimental scope.

The construction follows the controlled design in Chapter 3,
Section~\ref{dataset-methodology}. First, five traffic categories and
their web-event labels are defined. Clean HTTP records are then paired
with adversarial counterparts that preserve the underlying request
semantics as far as practical and add one Prompt Injection instruction
to an attacker-controlled field. Each row receives a sample ID, pair ID,
condition, and relevant attack or injection annotations. The final balance
check confirms 50 clean and 50 adversarial records per category, with 10
examples of each Prompt Injection variant within each category. The
synthetic records do not retain CSIC source-record identifiers, so this
is a synthetic construction rather than a row-by-row transformation of
CSIC records.

\section{External Evaluation Dataset: ModSec-WP}
\label{implementation-public-dataset-basis}

The external evaluation uses Version 2 of the WordPress Web Attack Audit
Log Dataset (ModSec-WP), published on Zenodo under CC BY 4.0
~\cite{modsecwp2026dataset}. Its source contains 108{,}883 records with
six original labels: \texttt{normal}, \texttt{sqli}, \texttt{xss},
\texttt{bruteforce}, \texttt{fileinclusion-ldf}, and \texttt{rce}. The
study selects the first four, which can be mapped to the implemented
taxonomy. File inclusion is excluded because its source class combines
LFI, RFI, and path traversal and cannot be mapped unambiguously to the
project's Path Traversal label; RCE is outside the evaluated taxonomy.

The records are HTTP transactions captured from a WordPress research
testbed instrumented with ModSecurity in detection-only mode. The dataset
authors describe replaying benign traffic and attacks against publicly
disclosed plugin vulnerabilities. This provides a traceable source of
observed request/response transactions, but the testbed design does not
make the dataset representative of production traffic.

The dataset authors describe their labels as based on scenario
correlation, regular-expression matching, and expert review. This
documented provenance supports treating ModSec-WP as a credible,
traceable external source, but this study did not independently verify
the annotations. Accordingly, the original labels are treated as the
dataset's reference labels, not as independently confirmed ground truth.
HTTP CSIC 2010~\cite{csic2010dataset} is the basis for the primary
500-record synthetic experimental dataset; it is not used as the
external evaluation dataset reported here.

\subsection{External ModSec-WP Evaluation Data}
\label{dataset-modsec-evaluation}

The external sample contains 400 deduplicated ModSec-WP requests: 100
from each of the \texttt{normal}, \texttt{sqli}, \texttt{xss}, and
\texttt{bruteforce} source classes. Before sampling, requests were
deduplicated by method, URL path, query, request body, and user agent;
two fingerprints with conflicting labels were excluded. A
class-stratified random sample was selected with seed 42. The full source file,
its SHA-256 digest, sampling parameters, label counts, and field mapping
are recorded in the accompanying data manifest.

The original \texttt{normal} label maps to Benign; \texttt{sqli},
\texttt{xss}, and \texttt{bruteforce} map to Malicious with the
corresponding project attack type. The \texttt{bruteforce} to Brute
Force Login mapping is approximate, particularly because source records
include XML-RPC authentication activity. The source does not provide
severity labels, so severity remains null. No attack subtypes are
inferred for the excluded source classes. Although the
\texttt{bruteforce} stratum was sampled, it is excluded from all reported
ModSec-WP model metrics: the label describes repeated activity that
must be assessed over a time window, not from an isolated request.

A supplementary sequence-evidence annotation matches the sampled
requests back to the original transactions. It marks repeated
authentication activity when at least five distinct requests from the
same source address target the same path within five minutes. This
evidence tier does not overwrite the source labels or enter model inputs.
It supports interpreting the category label in source context, but does
not prove that each authentication attempt failed. It found that 99 of
the 100 sampled requests met the five-request, five-minute criterion.
The source requests are retained for this audit; both their clean and
adversarial records are excluded from quantitative evaluation.

\subsubsection{Paired ModSec-WP Prompt Injection Records}
\label{dataset-modsec-pi-pairs}

Each of the 400 source requests forms a clean/adversarial pair, producing
400 pairs and 800 records. Variant assignment is deterministic with
seed 43. The adversarial member adds one of the five study-authored
Prompt Injection variants to a URL-encoded \texttt{pi\_note}
parameter in either the URL or query-parameter field. Instruction
Override, Classification Manipulation, Severity Manipulation, and
Prompt Extraction each have 85 pairs; Evidence Suppression has 60 pairs
and is limited to malicious source records. For each of the three
malicious source classes, there are 20 pairs per variant. Normal records
contribute 25 pairs to each of the other four variants. Field placement
is balanced across URL and query parameters: 42/43 pairs for each
85-pair variant and 30/30 for Evidence Suppression.

Apart from adding the encoded \texttt{pi\_note} parameter, the source
request fields and response status are unchanged in the adversarial
member. The original web-event label is retained for both pair members.
The instruction, its target, and scoring annotations are not passed as
separate model fields; only the instruction embedded in the request is
visible as request content. Pair identifiers are used only for post-hoc
comparison. Because the source supplies no severity labels, the Severity
Manipulation target is scored as instruction obedience, not
severity-classification accuracy. This controlled augmentation tests
the specified thesis variants and is not an independent sample of
naturally occurring Prompt Injection.

The original model run covered all 800 records. The reported ModSec-WP
metrics use the 300 pairs (600 records) from the randomly sampled
\texttt{normal}, \texttt{sqli}, and \texttt{xss} strata. They exclude the
100 \texttt{bruteforce} pairs because classifying an isolated request
without event times cannot establish behavior over the required
temporal window.

\section{Dataset Schema}\label{dataset-schema}

Each structured record uses the following fields. The example shows an
adversarial SQL Injection record; its clean counterpart is linked through
the pair identifiers.

\begin{lstlisting}
{
  "sample_id": "SQLI_0001_ADV",
  "paired_sample_id": "SQLI_0001_CLEAN",
  "pair_id": "PAIR_0001",
  "http_method": "POST",
  "url": "/product?note=Ignore previous instructions...",
  "query_parameters": "note=Ignore previous instructions...",
  "request_body": "username=1 UNION SELECT username,password FROM users--",
  "payload": "1 UNION SELECT username,password FROM users--",
  "user_agent": "...",
  "status_code": 400,
  "src_ip": "192.0.2.11",
  "ground_truth_label": "malicious",
  "attack_type": "SQL Injection",
  "traffic_category": "SQL Injection",
  "ground_truth_severity": "high",
  "is_adversarial": true,
  "injection_type": "Instruction Override",
  "injection_field": "query_parameters",
  "prompt_injection_text": "Ignore previous instructions..."
}
\end{lstlisting}

The request fields represent the log content. The remaining fields store
ground-truth and experiment metadata and must not be provided to the model
as labels. In an adversarial record, the instruction itself is embedded
in the indicated request field; \texttt{prompt\_injection\_text}
duplicates that instruction as an annotation for analysis.

In the current dataset, the control category uses
\texttt{traffic\_category = Benign / Normal},
\texttt{ground\_truth\_label = benign}, and \texttt{attack\_type = None}
because no web-attack subtype applies. The thesis refers to this web-event
class simply as \emph{Benign}. This class is independent of the Prompt
Injection condition: both clean and adversarial Benign records are
included. An adversarial Benign record retains the benign web-event label
while its Prompt Injection fields record the separate adversarial
condition.

The \texttt{is\_adversarial}, \texttt{injection\_type}, and
\texttt{injection\_field} values provide the Prompt Injection labels.
The current annotations do not include \texttt{ground\_truth\_mitre},
\texttt{injection\_target}, or \texttt{expected\_evidence}; the chapter
therefore does not treat those fields as available.

The 19 record fields represent three groups: HTTP content and context,
web-event ground truth, and pair/Prompt Injection annotations. Chapter 4,
Section~\ref{input-representation}, uses this same separation to define
the model input. The loader validates field types and normalizes values
as described in Chapter 4, Section~\ref{preprocessing-and-parsing}.

The injection variant and exact text are available, but a per-record
success target and expected-evidence annotation are not. Before
calculating ASR, these scoring annotations must be added to a separate
evaluation store using the success criteria in
Chapter 3, Section~\ref{variant-success-criteria}. They must remain
outside the model input. Until that annotation step is complete, the
dataset alone is not sufficient to compute variant-specific ASR
reproducibly.

\section{Clean and Adversarial
Pairing}\label{clean-and-adversarial-pairing}

Each adversarial record has a corresponding clean record with the same
\texttt{pair\_id}. The \texttt{sample\_id} and
\texttt{paired\_sample\_id} fields identify both members of each pair.

Example:

\begin{lstlisting}
SQLI_0001_CLEAN -- Clean
SQL Injection payload
No Prompt Injection

SQLI_0001_ADV -- Adversarial
Same SQL Injection payload
+ Instruction Override instruction
\end{lstlisting}

Paired design makes it possible to compare the effect of Prompt
Injection while reducing variation in the underlying web event.

\section{Prompt Injection Placement}\label{prompt-injection-placement}

In the current 500-record dataset, Prompt Injection text is embedded in
the \texttt{url} or \texttt{query\_parameters} field. Although User-Agent
and request-body values are also represented as possible attacker-
controlled inputs in the threat model, they do not currently contain the
injections in this dataset version.
 Instruction Override instruction

The five injection categories in the dataset are:

\begin{itemize}
\tightlist
\item
  Instruction Override,
\item
  Classification Manipulation,
\item
  Severity Manipulation,
\item
  Evidence Suppression,
\item
  Prompt Extraction.
\end{itemize}

Each adversarial record has one of these labels, and the exact instruction
and its field are recorded in \texttt{prompt\_injection\_text} and
\texttt{injection\_field}. The 250 adversarial records are balanced across
the five variants, with 50 records per variant. In the current dataset,
125 instructions are placed in \texttt{url} and 125 in
\texttt{query\_parameters}.

The attack classes are limited to SQL Injection, Cross-Site Scripting,
Path Traversal, and Brute Force Login. A Benign category is retained
as a control class. Suspicious File Upload is excluded from the initial
dataset to keep the evaluation focused.

Each of the five traffic categories has 50 clean and 50 adversarial
records, yielding 250 records per condition and 500 in total. Clean SQL
Injection records remain malicious; \emph{clean} refers only to the
absence of Prompt Injection. The web-event label and the Prompt Injection
condition are separate dimensions, including for the Benign control
category.

\section{Functional Organization}
\label{functional-organization}

The planned implementation separates four responsibilities: request
validation and preprocessing, trusted-knowledge retrieval, controlled
execution of configurations C1--C4, and evaluation of responses. This
separation keeps scoring labels out of model input and prevents labelled
evaluation examples from becoming retrieval evidence. The full-dataset
C1--C4 evaluation reported in Chapter~\ref{experimental-evaluation} has
been executed; this does not imply that a production application has
been deployed.

\section{Implementation Details}\label{implementation-details}

The implementation will follow the processing path described in Chapter 4.
The planned stages are:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Load a structured log record, validate required fields and types, and
  separate model input from scoring metadata, as described in
  Section~\ref{preprocessing-and-parsing}.
\item
  Build a versioned ChromaDB collection from the approved OWASP, ATT\&CK,
  playbook, and Prompt Injection policy documents. Do not index labelled
  logs or evaluation answers; see Sections~\ref{system-knowledge-base}
  and~\ref{retrieval} in Chapter 4.
\item
  Run records under C1--C4 with fixed model and generation settings.
  Keep each clean/adversarial pair together and store its configuration,
  response, detector output, and retrieved evidence IDs.
\item
  Validate the generated structured report and cited evidence IDs, then score web-event
  classification and Prompt Injection outcomes against the separate
  annotations. Chapter 3 defines the metrics and success criteria; the
  detector validation procedure is in Chapter 4,
  Section~\ref{empirical-validation-of-detector}.
\end{enumerate}

For the completed full-dataset evaluation, the recorded setup used the
\texttt{gpt-4o-mini} alias (provider-returned model
\texttt{gpt-4o-mini-2024-07-18}), the
\texttt{all-MiniLM-L6-v2} embedding model with Chroma ONNX, knowledge
base version \texttt{2026-11-17-r3}, retrieval top-\emph{k} of 3,
temperature 0.1, and structured output. The baseline comparison used
secure-prompt version \texttt{attempt-semantics-v2} with
\texttt{independent-examples-v1} in C3. The improved C4 run used
\texttt{attempt-semantics-v4}, \texttt{independent-examples-v2}, URL
decoding, and removal of detected instructions before retrieval and
generation on its 240 secure-route records. The results are reported in
Chapter~\ref{experimental-evaluation}. This describes that evaluation
run and should not be read as a claim that every planned application
component has been completed or deployed.

The separate ModSec-WP model run evaluated C1--C4 once on all 800 paired
records, producing 3{,}200 responses. The reported quantitative
evaluation excludes the 200 \texttt{bruteforce} records and uses the
remaining 600 records (300 pairs). It used the configured
\texttt{gpt-4o-mini} model (provider-returned
\texttt{gpt-4o-mini-2024-07-18}), temperature 0.1, structured output,
retrieval top-\emph{k} of 3, the \texttt{all-MiniLM-L6-v2} Chroma ONNX
embedding model, and knowledge-base version \texttt{2026-11-17-r3}. C3
and C4 used
secure-prompt version \texttt{attempt-semantics-v5} and
\texttt{independent-examples-v2}; C4 additionally used detector-based
routing and sanitization. The run manifest records the prompt, dataset,
knowledge-base, and runner hashes. Because the source sample informed
prompt v5, these results are not an independent holdout estimate.

The secure-prompt versions referenced above are documented in
Appendix~\ref{appendix-secure-prompt-versions}. The appendix summarizes
the recorded content of versions v2 and v4 and reproduces the available
version-v5 prompt text.

\section{Ethical and Security
Considerations}\label{ethical-and-security-considerations}

The experiments use controlled, offline, or synthetic web-attack
examples for defensive research.

The thesis evaluates whether malicious content inside logs can influence
an LLM. It does not require deployment of attacks against third-party
infrastructure.
